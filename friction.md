# AttackLens — Friction Audit

_Product-owner + customer-success review of onboarding, install, operate, and maintain surfaces._
_Last updated: 2026-07-23._

Framed by the customer journey and ranked by impact. Each item has concrete evidence
(`file:line`), the customer impact, and the recommended fix. Status column tracks what's
been actioned.

---

## 🔴 P0 — Onboarding blockers (break the first-run experience)

### 1. The "one-command installer" ships broken placeholder values
**Evidence:**
- `install.sh:27` → `REPO_URL=…github.com/your-org/attacklens.git` (placeholder → clone fails)
- `README.md:301` → `git clone <your-repo-url>`
- `install.sh:874` → `<your-server-ip>`
- `agent/os/macos/installer/generate_config.sh:27` → `MANAGER_URL=http://YOUR_MANAGER_IP:8080`

**Impact:** Time-to-first-value fails before step 1 — the single biggest silent-churn point.
**Fix:** real defaults, or a fail-fast preflight (`REPO_URL must be set`) + a `.env`-driven
`MANAGER_URL` prompt. **Status:** ☐ not started.

### 2. No single "golden path" — too many install routes & artifacts
**Evidence:**
- Two macOS packaging systems coexist: `agent/os/macos/installer/` **and** `agent/os/macos/pkg/`.
  Active = `pkg/` (ships v2.0.1, 2.2.0); `installer/` is older (only v2.0.0). Not signposted.
- 6 built pkgs across two version lines **and two product names**:
  `attacklens-agent-{1.1.0,2.0.1,2.1.0,2.2.0}`, `installer/…2.0.0`, plus `macintel-agent-2.0.0`.
- 4 overlapping quick-starts: `docs/QUICK_START.md`, `docs/installation/quick-start.md`,
  `agent/os/macos/installer/QUICKSTART.md`, `agent/os/macos/pkg/INSTALL_GUIDE.md`.

**Impact:** Decision paralysis + inconsistent support answers + larger maintenance surface.
**Fix:** one canonical installer, one "latest" pkg, retire `macintel-*` naming, collapse
quick-starts behind a single authoritative entry. **Status:** ◑ in progress — `docs/INSTALL.md`
router added + redirect banners on the redundant quick-starts (2026-07-23).

## 🟠 P1 — Trust & reliability (a security product must feel solid)

### 3. Default-insecure config is the path of least resistance
**Evidence:** `agent/os/macos/installer/generate_config.sh:39` auto-sets `TLS_VERIFY=false`
whenever `MANAGER_URL` is HTTP — the easiest setup ships plaintext + no cert verification, and
that config gets copied to prod.
**Impact:** Reputational for an EDR vendor; weakens the product's own threat model.
**Fix:** secure-by-default; make HTTP / `tls_verify=false` an explicit `--insecure` (lab) opt-in
with a loud warning. **Status:** ☐ not started.

### 4. Installs break often enough to need a 30 KB manual + a `repair` command
**Evidence:** `agent/os/macos/TROUBLESHOOT.md` catalogs 12+ distinct real install failures
(`command not found`, bad watchdog args, `Bootstrap failed: I/O error`,
**"Issue 5b — agent never starts after reboot, exit 78"**, HTTP 429 storms, rogue-server-on-port,
queue-full drops…). The headline `attacklens-service repair` command exists because installs
frequently land broken.
**Impact:** Each entry = a support ticket + eroded confidence.
**Fix:** convert the top 5 reactive fixes into preflight guardrails.
**Status:** ◑ partial — boot-persistence self-repair + reboot detection shipped 2026-07-23
(hardens Issue 5b); the rest remain reactive.

## 🟡 P2 — Scale & internal velocity (slower releases → slower customer fixes)

### 5. Repo-hygiene footguns
**Evidence:**
- **Recursive build tree:** `agent/os/macos/installer/pkg_build/root/Library/AttackLens/src/agent/os/macos/installer/pkg_build/…`
  — the packaging staging root contains a copy of the whole repo **including itself** (196 tracked
  files). It is regenerated by `installer/build_pkg.sh:99-106` (`rsync -a`), so it never belonged
  in git.
- **2 tracked `.pkg` build outputs** (~5.7 MB) under `installer/pkg_build/`.
- **22 built dashboard JS bundles tracked in git** (`manager/dashboard/static/assets/*.js`).
  ⚠️ These are **load-bearing**: `manager/Dockerfile:69` copies the prebuilt `manager/dashboard/static/`
  into the image and **CI does not run `npm run build`** (only the local `Makefile:147` does). So they
  must NOT be untracked until a build step is added to CI/Docker — otherwise deploys ship a UI with no JS.

**Impact:** Repo bloat, noisy diffs (assets deleted+re-added every build), mis-greps, edits to the
wrong source copy.
**Fix (sequenced):**
1. ✅ `.gitignore` the regenerated staging root + `.pkg` outputs; `git rm --cached` the 196-file
   recursive copy + 2 pkgs (done 2026-07-23 — files remain on disk, only untracked).
2. ☐ Add `npm run build` (or `make dashboard`) to `manager/Dockerfile` / `deploy.yml` **first**,
   then untrack `manager/dashboard/static/assets/` and gitignore it.
**Status:** ◑ step 1 done; step 2 (dashboard assets) deliberately deferred until CI builds them.

### 6. Agent enrollment is manual at fleet scale
**Evidence:** `ENROLL_TOKEN` is optional and hand-pasted
(`agent/os/macos/installer/generate_config.sh:105`). No self-serve "copy this install command with
your token baked in" flow from the dashboard.
**Impact:** Per-agent manual config doesn't scale; slows fleet onboarding.
**Fix:** dashboard-generated per-tenant enroll command (standard EDR onboarding motion).
**Status:** ☐ not started.

## Summary

The platform depth (async ingest, tiered storage, MITRE correlation, AI analysis) is strong — the
friction is concentrated at the **edges**: getting in the door (P0) and staying trustworthy/tidy
(P1–P2). Fixing **P0 alone** would move activation the most. Recommended order: **1 → 2 → 3 → 6 → 4 → 5**.
